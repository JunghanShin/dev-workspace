# 명령 길: 누가 명령할 수 있나, 운용 모드와 개발 모드

| 항목 | 내용 |
|---|---|
| 문서 | 워크스페이스 플랫폼 설계(design.md 4.1 원칙 13·17, 6.6.7.4)의 명령 길 부분. 그림 `command-path.svg` |
| 바꾸는 것 | 워커 명령을 아무나 보낼 수 있던 것을, **허용된 곳만** 보내고 **운용 모드에서는 운용 조작만** 되게 한다. 들어온 명령은 보낸 곳과 함께 남긴다 |
| 하지 않는 것 | 여러 곳이 동시에 명령할 때 누가 이기는지 조정(조종권·우선순위). 그것은 판단이라 매니저의 일이다(원칙 11, mission-manager "조종 권한"). 플랫폼은 도착한 순서대로 넘긴다 |
| 바탕 | 0.40~0.54의 층 구조(게이트웨이·process-manager·워커), 계약(6.6.7.1), Manager API를 쓰는 워커(6.5) |

## 1. 하는 일과 품질 목표

| 목표 | 뜻 | 확인 |
|---|---|---|
| ① 허용된 곳만 | 워커 명령 소켓은 화면(게이트웨이)과 연결 선언에 적힌 곳(외부 연동 워커, 나중에 매니저)의 명령만 받는다. 보드 안 아무 프로그램이 소켓에 직접 붙어 명령하지 못한다 | libworker 시험(허용·거절·기록만), process-manager 수락 시험(`peers.json` 내용) |
| ② 운용 중 실수 방지 | 운용 모드에서는 역할 명령(짐벌 각도·비행 모드 등)과 읽기만 된다. 설정 바꾸기·시작/정지·워커 전용 명령은 개발 모드에서만. 화면·원격·외부 연동 워커 모두 같은 규칙 | 게이트웨이 수락 시험(모드 × 명령 종류), process-manager 수락 시험(Manager API 쓰기 × 모드) |
| ③ 누가 했나 보임 | 모든 명령에 보낸 곳이 붙어 기록되고, 워커 상태에 마지막 명령과 보낸 곳이 보인다. 충돌(화면과 외부가 번갈아 명령)은 기록으로 확인한다 | 수락 시험(기록 줄의 `from`, `get_status`의 `last_command`) |
| ④ 단독 실행 그대로 | 워커를 워크스페이스 없이 띄우면(허용 목록 파일 없음) 지금처럼 막지 않는다 | libworker 시험 |
| ⑤ 판단 없음 | 플랫폼은 표대로 넣고 빼기만 한다. 무엇을 허용할지는 연결 선언(데이터)과 계약(정의 파일)이 정한다 | 설계 검토 |

## 2. 명령하는 곳과 길

```text
 브라우저(로그인 세션)   ─┐
 원격 화면(토큰)          ─┼─ HTTP ─▶ nginx ─▶ 게이트웨이 ─────────┐   검사 ①: 모드 × 사용자 역할 × 명령 종류
                          │                   (보낸 곳 from을 붙임)│
 외부 장비 ─(외부 프로토콜)─▶ 외부 연동 워커 ──────────────────────┼─▶ 워커 명령 소켓    검사 ②: 보낸 프로세스 × 허용 목록
                                  └─ Manager API ─▶ process-manager │                    (process-manager가 만든 peers.json)
                                                   검사 ③: 모드     │
 (나중) 매니저 ─────────────────────────────────────────────────────┘

 QGC ─▶ mavlink-router ─▶ PX4      워크스페이스 밖. 결과만 기체 워커가 보고 출처 external로 기록
```

| 명령하는 곳 | 알아보는 방법 | 보낸 곳 이름(`from`) |
|---|---|---|
| 화면 | 게이트웨이에 로그인 세션으로(신분 확인 꺼짐이면 모두 화면) | `screen` |
| 원격 화면·외부 프로그램(HTTP) | 게이트웨이에 토큰으로 | `remote:<토큰 이름>` |
| 외부 연동 워커·다른 워커 | 워커 명령 소켓에 직접. 커널이 알려 준 상대 pid의 프로세스 그룹 = 그 워커 | 워커 id |
| 매니저(나중) | 워커와 같음 | 매니저 id |
| 그 밖 | 허용 목록에 없음 | `unknown:<pid>` |

- **화면은 늘 허용.** 화면은 장비 자체다. 연결 선언에 적지 않아도 모든 워커에 명령할 수 있다(운용 모드의 제한은 받음)
- **동시 명령은 조정하지 않는다.** 화면과 외부 연동 워커가 함께 명령하면 도착한 순서대로 실행된다. 번갈아 덮어쓰는 일(핑퐁)은 운용 절차·외부 시스템이 피하고, 기록(`from`)으로 확인한다. 조정이 필요해지면 매니저 규칙으로 넣는다(플랫폼 코드는 그대로)

## 3. 명령 종류와 모드

명령 종류는 워커 계약으로 가린다(design.md 6.6.7.1).

| 종류 | 무엇 | 운용 모드 | 개발 모드 |
|---|---|---|---|
| 읽기 | `get_status`, 계약에 `"read": true`인 명령 | 됨 | 됨 |
| 역할 명령 | 워커가 내보내는 역할 정의(`io/<역할>.json`)의 명령. 예: 짐벌 각도, 줌, 비행 모드 | 됨(허용된 곳) | 됨 |
| 운용 조작 | 워커 정의·조각의 명령 중 `"operate": true`로 표시한 것. 예: 영상 송출 켜기·끄기(libvideo `stream.start`·`stop`) | 됨(허용된 곳) | 됨 |
| 워커 전용 명령 | 워커 정의(`io/self.json`)에만 있는 명령, **어느 계약에도 없는 명령** | 막음 | 됨 |
| 관리 조작 | 설정·프리셋·자동 시작 바꾸기, 시작/정지, 연결 선언 바꾸기, 제품 빌드 | 막음 | 됨 |

- **모드:** 운용 모드(기본) / 개발 모드. 워크스페이스 설정 화면의 토글(관리 역할만), 저장하지 않음(시작하면 운용). 바꾼 시각·사람과 그동안의 명령은 기록(원칙 17). 모드 주인은 게이트웨이, process-manager는 알림을 받아 `access_mode`로 들고 `peers.json`에 반영
- **사용자 역할은 그대로:** 역할 명령은 `operator` 이상, 워커 전용 명령·관리 조작은 `maintainer`(design.md 6.4·`docs/gateway.md` 3장). 모드는 그 위에 더 거는 조건이다
- **막을 때 답:** `403 {"error": {"code": "forbidden", "message": "development mode required"}, "need": "development"}`. 화면은 이 답을 "개발 모드에서만 됩니다(워크스페이스 설정에서 켜기)"로 보여 주고, 운용 모드에서는 그 버튼을 미리 흐리게 한다

## 4. 허용 목록

### 4.1 연결 선언: `commanders`

`<데이터>/config/connections.json`(design.md 6.6.7.4, 보드마다·프로필로)에 역할마다 명령해도 되는 곳을 적는다. 화면은 적지 않는다(늘 허용).

```json
{
  "connections": [],
  "commanders": {
    "cam.gimbal": ["ext-ops"],
    "vehicle-link": ["ext-ops"]
  }
}
```

| 키 | 뜻 |
|---|---|
| `<워커>.<역할>` | 그 워커가 내보내는 그 역할의 명령 |
| `<워커>` | 그 워커가 내보내는 모든 역할의 명령 |
| 값 | 명령해도 되는 워커 id(나중엔 매니저 id) 목록 |

process-manager 검사(틀리면 그 항목만 오류로 표시, 워커 기동은 막지 않음): 워커가 있는지, 그 워커가 그 역할을 내보내는지(`io.json`), 명령하는 곳이 있는 워커인지, 명령하는 곳이 그 역할을 쓴다고 적었는지(`uses`, 없으면 경고만). op `get_connections`(읽기)·`set_connections`(쓰기, 관리 조작), REST `GET·PUT /connections`.

### 4.2 `peers.json`: process-manager가 만들고 워커가 읽는 표

process-manager가 연결 선언·계약·모드·지금 떠 있는 프로세스로 만든다. 워커는 판단 없이 표만 본다.

`<데이터>/run/peers.json`(0600, 임시 파일 → rename):

```json
{
  "version": 1, "guard": "warn", "mode": "operation", "boot_id": "…", "written_at_ms": 0,
  "peers": {
    "gateway": {"pid": 812, "trusted_from": true},
    "ext-ops": {"pgid": 1290}
  },
  "workers": {
    "cam": {
      "read": ["get_status", "gimbal.get_angle"],
      "allow": {
        "gateway": "*",
        "ext-ops": ["gimbal.set_angle", "gimbal.center", "gimbal.rate"]
      }
    }
  }
}
```

| 칸 | 뜻 |
|---|---|
| `guard` | `off`(보지 않음) · `warn`(어긋나면 기록만, **기본**) · `enforce`(거절). Manager 설정 `command_guard` |
| `peers` | 명령하는 곳 → 알아볼 프로세스. 워커·매니저는 프로세스 그룹(`pgid`, process-manager가 새 그룹으로 띄움), 게이트웨이는 `pid`(게이트웨이가 `manager-rest.sock`에 붙을 때 커널이 알려 준 pid. 따로 등록하지 않음). `trusted_from`: 명령의 `from` 칸을 믿는 곳(게이트웨이만) |
| `workers.<id>.read` | 늘 허용(읽기) |
| `workers.<id>.allow` | 명령하는 곳 → 허용 명령. `"*"`는 전부. 운용 모드면 4.1의 역할 명령만(워커 이름만 적었으면 `operate` 명령도), 개발 모드면 그 워커의 모든 명령(`"*"`). 게이트웨이는 늘 `"*"`(모드 검사는 게이트웨이가 사용자 역할과 함께 함) |

- **다시 만드는 때:** 워커가 뜨거나 끝날 때(pgid), 게이트웨이가 다시 붙을 때(pid), 연결 선언·계약·모드가 바뀔 때. 파일만 바꾸고 워커를 다시 시작하지 않는다
- **워커에 알리기:** 띄울 때 환경 변수 `WORKSPACE_PEERS_FILE`(경로). 설정 파일 키가 아니라 환경 변수인 것은 예전 libworker로 빌드된 워커가 모르는 설정 키에 멈추지 않게(모르는 환경 변수는 무시됨). 워커(libworker 0.10)는 명령이 올 때 파일 바뀐 시각을 보고 바뀌었으면 다시 읽는다. 없으면(단독 실행) 보지 않는다(목표 ④)

## 5. 검사 세 곳

| 곳 | 무엇을 | 어떻게 |
|---|---|---|
| ① 게이트웨이 | 화면·원격의 요청 | 사용자 역할(지금처럼) + 3장 표(모드 × 종류). 명령 종류는 그 워커의 계약(`GET /workers/{id}/io`와 같은 것, 계약 파일이 바뀌면 다시 읽음)으로 가린다. 넘길 때 `from`을 붙인다. 기록 줄에 `from` |
| ② 워커 명령 소켓(libworker) | 소켓에 붙은 모든 상대 | 상대 pid(`SO_PEERCRED`) → `peers`에서 찾기(pid 같음, 또는 `getpgid(pid)`가 pgid와 같음) → 그 워커의 `read`·`allow`에 명령이 있나. 신뢰하는 곳(게이트웨이)이면 명령의 `from`을 쓰고, 아니면 찾은 이름을 `from`으로(명령에 적힌 `from`은 무시). `warn`이면 어긋나도 실행하고 이벤트·로그 한 줄, `enforce`면 `forbidden` |
| ③ process-manager | 외부 연동 워커의 Manager API 쓰기(`manager-<워커>.sock`) | 운용 모드면 관리 조작 op(시작·정지·설정·프리셋·자동 시작) `forbidden "development mode required"`. 화면의 같은 요청은 게이트웨이가 먼저 막는다 |

- **켜는 단계:** ①·③은 바로 막는다(사람이 바로 확인할 수 있음). ②는 `warn`으로 시작해 보드에서 어긋나는 접속이 없는지 기록으로 본 뒤 `enforce`(Manager 설정 `command_guard`)
- **명령 봉투:** 9.6 `{"cmd", "args"}`에 `"from"`을 더한다(게이트웨이만 넣음). 워커 모듈은 `from`을 받아 쓸 수 있지만 판단에 쓰지 않는다
- **마지막 명령:** libworker가 읽기가 아닌 명령을 받을 때마다 `get_status` 공통 칸 `last_command: {"cmd", "from", "t_mono_ns", "ok"}`(공통 정의 `common.json`)를 갱신한다. 화면은 이것으로 "마지막 명령: 누구"를 보여 준다

## 6. 끊겼을 때

| 상황 | 동작 |
|---|---|
| `peers.json`이 없거나 깨짐(워크스페이스 안) | `warn`처럼 동작(실행하고 기록). 깨진 파일이면 마지막으로 읽은 표 |
| 게이트웨이가 다시 시작해 pid가 바뀜 | 게이트웨이가 `manager-rest.sock`에 다시 붙는 순간(시작 직후 첫 요청) process-manager가 표를 다시 씀. 그 사이 게이트웨이 명령은 `warn`이면 기록만, `enforce`면 거절될 수 있음(화면에서 다시 누르면 됨) |
| process-manager가 죽음 | 시작 셸이 워크스페이스를 내림(6.3) |
| 계약 파일이 없는 워커 | 그 워커의 명령은 모두 워커 전용(운용 모드에서 막힘). 점검의 미준수 목록에 이미 나옴 |

## 7. 시험

| 무엇 | 어떻게 |
|---|---|
| 게이트웨이 | 수락 시험: 운용·개발 × 읽기·역할·전용·관리 조작의 답, 403 모양, 원격 토큰의 `from`, 기록 줄 `from`, 계약 없는 명령 |
| process-manager | 수락 시험: `commanders` 검사, `peers.json` 내용(모드·워커 시작/정지·게이트웨이 다시 붙음에 따라), Manager API 쓰기 × 모드 |
| libworker | 단위 시험: `WORKSPACE_PEERS_FILE` 없음 → 막지 않음, `warn` → 실행 + 기록, `enforce` → 허용·거절, `from` 믿기·무시, `last_command` |
| 보드 | `warn`으로 며칠: 기록에 어긋난 접속이 없는지 → `enforce` |
